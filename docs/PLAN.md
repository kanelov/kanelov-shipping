# План: собствен WooCommerce плъгин за доставка с Еконт (и други куриери)

Дата: 2026-09-20. Статус: чернова за обсъждане, преди да се пише код.

## 1. Извод от анализа на платения плъгин (MrejaNet, v1.8.7)

Прегледах целия код. Важното за нас:

**Как е направен и защо не искаме да го копираме**

- Ползва **старото XML API** на Еконт (`econt.com/e-econt/xml_service_tool.php`, `xml_parcel_import2.php`) с потребител и парола в тялото на заявката. Еконт от години поддържа и документира **JSON API** (`ee.econt.com/services/...`) с HTTP Basic auth. Нашият плъгин ще е върху JSON API, тоест транспортният слой ще е принципно различен.
- Номенклатурите (градове, офиси, улици, квартали) **не се теглят от Еконт**, а от сървъра на разработчика `resources.mreja.net`. При всяко обновяване там отиват хостнеймът и имейлът на администратора. Това е и механизмът, чрез който той знае къде е инсталиран плъгинът.
- Лицензионната проверка: `licensing.mreja.net/license_check.php` се вика при всяко зареждане на страница (кеширано с transient), изпраща хостнейм и админ имейл по обикновен HTTP. При отговор `no` плъгинът зарежда празен JS и чекаутът спира да работи. Има и защита срещу смяна на адреса на лиценз сървъра.
- Всяка товарителница носи таг `<mediator>mrejanet</mediator>`, тоест разработчикът е регистриран като посредник при Еконт за твоите пратки.

**Лоши практики, които ще избегнем**

- Директно достъпен PHP файл (`fast-ajax`), който чете `wp-config.php` с `eval()` и отваря сурова mysqli връзка без никаква защита.
- `sslverify => false` към всички външни сървъри, включително канала за обновления по HTTP (уязвимост тип подмяна на ъпдейт).
- Цената за доставка се взима от скрито поле в браузъра на клиента, тоест клиентът може да си я промени.
- Неекраниран SQL и HTML на много места, лицензионното съобщение се вкарва в админа без екраниране.
- Кеш на отговорите на Еконт (с имена, телефони, адреси на клиенти) в `wp-content/econt/` без защита.
- ~1.2 MB стари библиотеки (OpenLayers 5 от 2018, ol-ext, select2 4.0.13, colorbox, tooltipster) плюс 4.8 MB source map, зареждани на всяка страница освен ако не е включена опция.
- Блоковият чекаут е закърпен с `setInterval` на 500 ms, който пренаписва React DOM.
- Полуизтрита поддръжка за Румъния и Гърция, дублиран код, мъртви настройки.

**Добри идеи, които ще запазим като концепция (не като код)**

- Едно общо поле „населено място“ за трите вида доставка.
- Проверка дали кошницата се побира в Еконтомат (АПС) преди да се предложи.
- Прагове за безплатна доставка поотделно за офис, АПС и адрес.
- Таблица за "кой плаща доставката" по стойност на поръчката.
- Запомнен адрес за регистрирани клиенти в „Моят акаунт“.
- Съкратено описание на пратката от имената на продуктите, минимално тегло по подразбиране.
- Кутия в поръчката с калкулация, генериране, изтриване, печат и проследяване.
- Колона и масово действие в списъка с поръчки.

**Авторски права.** Няма да копираме нито ред. Различно API, различна архитектура, различни имена на файлове, класове, настройки и мета ключове, собствен JS без техните библиотеки. Ползваме кода им само за да знаем какви функции очакваш и какви грешки да не повтаряме.

## 2. Възможно ли е

Да. Всичко, което искаш, е достъпно през публичното JSON API на Еконт:

| Нужда | Еконт услуга (JSON API) |
|---|---|
| Градове, офиси, АПС, улици, квартали | `Nomenclatures/NomenclaturesService.getCities/getOffices/getStreets/getQuarters` (офисите носят флаг за АПС) |
| Профил, адреси на подателя, споразумения за наложен платеж, шаблони инструкции | `Profile/ProfileService.getClientProfiles` (връща `cdPayOptions`, `instructionTemplates`, адреси) |
| Цена за доставка | `Shipments/LabelService.createLabel` с режим `calculate` |
| Товарителница | `Shipments/LabelService.createLabel` с режим `create` (връща номер и PDF линк) |
| Изтриване | `Shipments/LabelService.deleteLabels` |
| Проследяване | `Shipments/ShipmentService.getShipmentStatuses` |
| Заявка за куриер | `Shipments/ShipmentService.requestCourier` |
| Демо среда | `demo.econt.com/ee/services/` с demo/demo |

Товарителницата, създадена през API с твоите потребителски данни, се вижда в ee.econt.com веднага, защото е в твоя профил.

Има и работещи отворени референции (не за копиране, а за сверяване на формата на заявките): официалният плъгин на Еконт „Deliver with Econt“ (GitHub bogui/econt-woocommerce), Laravel обвивка gdinko/econt, плъгин „BG Couriers“ на wordpress.org.

## 3. Архитектура

Работно име: **`kanelov-shipping`** (ще го уточним). Един плъгин, ядро плюс адаптери за куриери.

```
kanelov-shipping/
  kanelov-shipping.php            зареждане, проверки за WC/PHP, HPOS декларация
  src/
    Core/                         Plugin, Settings, Assets, Installer (таблици), Logger
    Carrier/                      CarrierInterface + AbstractCarrier
      Econt/                      EcontApi, EcontCarrier, EcontShippingMethod,
                                  EcontNomenclatureSync, EcontLabelBuilder
      BoxNow/                     (фаза 2, същият интерфейс)
    Checkout/                     Classic (полета + валидация), Blocks (Store API extension),
                                  DeliveryData (общ обект за избор на клиента)
    Admin/                        OrderMetabox, OrdersListColumn, BulkActions, SettingsPage
    Rest/                         вътрешни REST маршрути за търсене (заместват admin-ajax)
  assets/
    src/checkout-blocks/          React компонент за блоковия чекаут (@wordpress/scripts)
    src/checkout-classic/         vanilla JS за класическия чекаут
    src/admin/                    JS за кутията в поръчката
  languages/
```

**Принципи**

- PHP 8.1+, WooCommerce 9+, HPOS от първия ден (само CRUD на поръчки, никакви `get_post_meta` за поръчки).
- Без външни PHP библиотеки. Заявки през `wp_remote_post` с включена TLS проверка.
- Търсене на градове и офиси през **WP REST API** (`/wp-json/kanelov-shipping/v1/...`) с кеш, без admin-ajax и без директни PHP файлове.
- Собствени таблици само за номенклатурите (градове, офиси, улици, квартали). Товарителниците се пазят като **мета в поръчката** с префикс `_ks_` (скрити от Custom Fields), плюс една таблица за пратки, ако ти трябва отчет по всички сайтове (ще питам).
- Ежедневна синхронизация на номенклатурите с Action Scheduler (вграден в WooCommerce), плюс бутон за ръчна.
- Цената за доставка се смята **на сървъра** и се пази в WC сесията, клиентът никога не я праща.
- Всички изходи екранирани, всички заявки с nonce и capability, всички SQL през `$wpdb->prepare`.
- Без jQuery библиотеки от 2018. За блоковия чекаут React компонент, компилиран с `@wordpress/scripts`. За класическия чекаут малък vanilla JS с търсене през REST. Карта на офисите (ако я искаш) с Leaflet или MapLibre, като отделна опция.
- Данните на подателя, споразуменията и шаблоните идват от `getClientProfiles` и се кешират като option, с бутон „Обнови профила“.

**Интерфейс на куриера** (за да е готово за BoxNow):

```
interface CarrierInterface {
  id(), label(), delivery_types()          // door | office | locker
  search_cities($q), get_offices($city, $type), get_streets($city, $q)
  calculate(DeliveryData, WC_Cart|WC_Order): Price
  create_label(WC_Order, LabelOptions): LabelResult
  delete_label(WC_Order): bool
  track(WC_Order): TrackingResult
  request_courier(...)                      // по избор
}
```

## 4. Функционалност по слоеве

### 4.1 Чекаут (клиент)

- Стандартни полета: **име, фамилия, телефон, имейл**. Всичко друго от WooCommerce адреса се скрива, когато е избран Еконт (без изисквания за адрес 1, град, пощенски код).
- Метод за доставка „Еконт“ с три вида: **до офис, до Еконтомат (АПС), до адрес**. Показват се само разрешените от настройките. АПС се предлага само ако пратката се побира (размери и тегло, конфигурируеми).
- Едно поле „населено място“ с търсене, после офис/АПС със търсене (име и адрес), или улица + номер (+ квартал, бл., вх., ет., ап., бележка) за адрес.
- Цената се преизчислява при всяка смяна на вида и мястото. Ако има безплатна доставка над праг, показва се 0.
- Запазен избор за регистрирани клиенти (user meta) и за гости (localStorage), за да не се въвежда повторно.
- Един и същ функционален набор в **класически и блоков** чекаут. В блоковия ползваме Store API extension data и `woocommerce_store_api_checkout_update_order_from_request`, без DOM хакове.
- Blocksy: работим с нативната WooCommerce маркировка на полетата, без `!important`, за да поеме темата стиловете. Тестваме с Blocksy при класически и блоков чекаут.
- След поръчка: адресът за доставка и фактуриране в WooCommerce се попълва с четим текст („Еконт офис Пловдив Тракия, ул. ...“), за да се вижда навсякъде в админа и имейлите.
- Наложен платеж: WC „Плащане при доставка“ остава; плъгинът само го скрива, ако си забранил НП за даден вид доставка.

### 4.2 Админ, настройки

Раздел в WooCommerce > Доставка > Еконт (плюс възможност за добавяне в зони, ако искаш различни правила):

- Среда (демо/реална), потребител, парола; бутон „Тест на връзката“.
- Подател: фирма, лице, телефон, имейл; изпращане от офис / адрес / АПС, избрани от адресите в профила ти.
- **Споразумение за наложен платеж** (падащо меню от `cdPayOptions` в профила): това е споразумението, при което Еконт събира НП и го превежда по банка.
- **Кой плаща доставката**: получател (НП + доставка), подател (по споразумение/кредит), или таблица по стойност на поръчката. Праг за безплатна доставка поотделно за офис / АПС / адрес.
- Пратка: тегло по подразбиране при продукт без тегло, минимално тегло, размери по подразбиране, брой пакети, тип (пакет/документ/палет), описание (имена на продукти / номер на поръчка / двете), максимална дължина на описанието.
- Услуги: SMS известие, обявена стойност, обратна разписка, фактура преди плащане, преглед/тест преди плащане, инструкции (шаблони от профила), избор на ден за доставка.
- Автоматизация: автоматично създаване на товарителница при статус X, смяна на статус след създаване, имейл до клиента с номер за проследяване.
- Чекаут: разрешени видове доставка, вид по подразбиране, карта (вкл./изкл.), геолокация, ограничения за АПС.

### 4.3 Админ, поръчка

- Кутия „Еконт“ в поръчката: избраният от клиента вид и място, бутон „Редактирай“ (същите полета като в чекаута, с търсене), тегло/размери/пакети/описание с предварително попълнени стойности, опции за НП и услуги, бутони **Изчисли**, **Създай товарителница**, **Изтрий**, **Печат PDF** (А4 и етикет), **Проследяване** (статусите от Еконт), **Заявка за куриер**.
- Колона в списъка с поръчки с номер на товарителницата и линк към PDF; масово действие „Създай товарителници“ през Action Scheduler (без loopback HTTP заявки).
- Всичко се записва в мета на поръчката: номер, PDF линк, дата, сума НП, история на статусите. Изтриването първо пита Еконт, после чисти локално.

### 4.4 Съвместимост със стари поръчки

Старите поръчки имат мета `Econt_*` от платения плъгин. Ще добавим четене само за показване (read-only), за да не губиш информация при превключване. Няма да пишем в тези ключове.

## 5. Поддръжка и обновления

- **Разпространение**: частно GitHub хранилище с releases. Малък updater в плъгина (Plugin Update Checker е с MIT лиценз и може да се ползва легално) с проверка през HTTPS и GitHub token, за да получават всичките ти сайтове обновление от Разширения > Обновления. Без лиценз сървър, без телеметрия.
- **Кога трябва ъпдейт**. Плъгинът зависи от три неща: WooCommerce (особено Blocks Checkout и Store API), WordPress и Еконт API. Практика:
  - WooCommerce излиза с нова версия примерно на всеки месец. Ще следим changelog-а за промени в `wc/store` и checkout blocks. Плъгинът ще декларира „WC tested up to“ и ще показва предупреждение в админа, ако WC е по-нов от тестваната версия.
  - Еконт JSON API е стабилно от години и се разширява без счупване. Ще логваме грешки от API и ще показваме известие в админа при грешен отговор.
  - Пускаме тестова версия на един сайт (staging), после на останалите.
- **Тестове**: PHPUnit за построяване на заявките към Еконт и за ценообразуването; Playwright тест на чекаута (класически и блоков) с Blocksy на локален WP.

## 6. Фази

1. **Фаза 0, подготовка** (след отговорите): ново хранилище, локална WP среда с Blocksy, демо профил на Еконт, скелет на плъгина, синхронизация на номенклатурите, тест на връзката.
2. **Фаза 1, чекаут**: класически чекаут с трите вида доставка, търсене, цена, запис в поръчката, скриване на излишните полета, запомнен адрес.
3. **Фаза 2, админ**: настройки, профил и споразумения, кутия в поръчката, товарителница (създаване, изтриване, PDF, проследяване), колона и масово действие, автоматизация и имейл.
4. **Фаза 3, блоков чекаут**: React компонент, Store API extension, същите функции като класическия.
5. **Фаза 4, стабилизация**: тестове, логове, обновления през GitHub, инсталация на първия реален сайт с демо среда, после реална среда.
6. **Фаза 5, BoxNow**: адаптер със същия интерфейс, избор на шкаф от карта/списък, ваучери, проследяване.

| Споразумения | Споразумение за събиране на НП по банка (избира се от профила), SMS известие включено, куриерската услуга по споразумение (кредит). НП = обща сума на поръчката вкл. платената доставка. |
| Тегло и описание | Тегло от продукта; при липса, тегло по подразбиране (настройка, 0,5 кг), минимално тегло 0,1 кг. Описание: номер на поръчка + продукти, съкратено до 100 знака. Брой пакети 1, променя се в админа. |
| Автоматизация | Товарителницата се създава ръчно от админа. Без отделен имейл: линкът за проследяване влиза в стандартния имейл „Изпълнена поръчка“ и в „Моят акаунт“. |
| Карта | Списък с търсене по подразбиране; картата се отваря по желание с бутон (свита), не е постоянно на екрана. |
| Плащания | Само стандартните WooCommerce методи (НП, WooPayments карта, банка, PayPal). Без EcontPay. |
| Език | Само български. |
| Стари поръчки | Не се четат. |
| BoxNow | Същият плъгин, като втори куриер (един чекаут, едни настройки). В интерфейса не се показва, докато не е готов; отделен плъгин не е нужен. |

**Забележка за сайта.** Активен е GPL плъгинът „Bulgarisation for WooCommerce“ (Autopolis), който също съдържа Еконт метод за доставка. Той ще остане само за българизацията (фактури, ЕИК и т.н.); неговият Еконт метод не трябва да е добавен в зоните за доставка, за да няма два Еконт метода. Понеже е GPL, кодът му е легална референция за формата на заявките към JSON API.

**LiteSpeed Cache.** REST маршрутите за търсене връщат публични данни и могат да се кешират. Чекаут страницата LiteSpeed не кешира по подразбиране. Ще проверим на staging.
